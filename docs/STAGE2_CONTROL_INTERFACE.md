## 一、修正上一份报告的错误

### 1.1 我之前的错误说法

`STAGE2_CONTROL_REPORT.md` §3.2 说：

> "⚠️ **部分完成**（reset ✅, 真 step ❌）"
> "`sim` 的 `StartTime/StopTime` 方式**每次都会从 StartTime 重新初始化状态**，**不是真正的增量 step**"

**这个判断是错的。** 真 step 完全可行，我用错了 API。

### 1.2 正确的方法

**关键 API**：
```matlab
set_param(MDL, 'SaveFinalState', 'on');
set_param(MDL, 'FinalStateName', 'xFinal');
set_param(MDL, 'SaveCompleteFinalSimState', 'on');

% 每步：
set_param(MDL, 'LoadInitialState', 'on');
set_param(MDL, 'InitialState', 'xFinal');
set_param(MDL, 'StartTime', num2str(t_start));
set_param(MDL, 'StopTime', num2str(t_end));
sim(MDL);
```

**之前失败的原因**：只改了 `StartTime/StopTime`，没有 `SaveFinalState` + `LoadInitialState`，所以每次都从零状态开始。

## 三、耗时与瓶颈分析

### 3.1 耗时分解

| 环节 | 耗时 | 说明 |
|---|---|---|
| `Setup_Simulation` | **3.53 s** | 重新构建仿真配置 |
| `sim` 固定开销 | **8.22 s** | 模型检查+编译+工作区同步 |
| `sim` 数值积分 | **≈ 0 s/s** | 几乎可忽略 |
| **单步总计** | **8.06 s** | |

### 3.2 线性拟合证据

| 仿真时长 (s) | 耗时 (s) | 每 0.105s 折算 |
|---|---|---|
| 0.015 | 8.587 | 60.11 |
| 0.105 | 7.662 | 7.66 |
| 0.420 | 8.225 | 2.06 |
| 1.050 | 7.820 | 0.78 |

**拟合**：`t(sim) = 8.217 − 0.362 × dur`

**关键解读**：
- **截距 8.22 s** → 固定开销
- **斜率 −0.36 s/s** → 数值积分几乎不占时间（负值来自测量噪声）
- **仿真的时长对耗时几乎无影响**（0.015s 和 1.05s 的耗时都是 8 s 左右）

### 3.3 ★ 瓶颈定位

| 环节 | 占单步总耗时 |
|---|---|
| **Setup_Simulation** | **30.5%** |
| **sim 固定开销** | **71.0%** |
| 数值积分 | **≈ 0%** |

**结论**：
> **单步耗时的 101% 来自"准备"（Setup + 模型检查），而非"计算"。**
>
> **这意味着：仿真时长再短也要 8 s，缩短控制周期不能提速。**

### 3.4 实时性判断

| 项 | 值 |
|---|---|
| 控制周期 | 0.105 s |
| 单步耗时 | 8.06 s |
| **实时倍率** | **76.8×** |

**❌ 不能实时。但这不是「Simulink 算得慢」，而是「MATLAB 调用开销大」。**

## 四、替代方案分析（可验证）

### 4.1 方案 A：Simulink Coder 生成 MEX/C 代码

**原理**：把 Simulink 模型编译成独立可执行代码，消除 MATLAB 解释器开销。

| 项 | 预估 |
|---|---|
| 编译时间 | 5–30 分钟（一次性）|
| 单步耗时 | **1–10 ms**（预期降 3 个数量级）|
| 实时性 | ✅ 可满足 0.105 s |
| 风险 | 模型含 T-MATS/EMTAT 自定义块，可能不支持代码生成 |

**验证方式**：
```matlab
slbuild('AGTF30SysDyn_PExPIn')   % 尝试生成代码
% 若成功 -> 测量生成代码的执行时间
% 若失败 -> 查看不支持块清单
```

**这是最值得优先验证的路径。**

### 4.2 方案 B：MATLAB Engine 常驻 + 减少数据回传

**原理**：Python 通过 `matlab.engine` 常驻连接，避免每次启动 MATLAB。

| 项 | 当前 | Engine 常驻 |
|---|---|---|
| MATLAB 启动 | 已含在 8s 内 | 一次 30–60 s |
| 单步调用 | 8.06 s | **仍 8.06 s** |
| 数据序列化 | 0 | +10–50 ms |

**结论**：**Engine 常驻不能解决 8 s 固定开销**（瓶颈在 Simulink 编译检查，不在 MATLAB 启动）。

**但可以消除 `Setup_Simulation` 的 3.53 s**（如果改成直接改 `MWS.In` 参数）：
```matlab
% 不做 Setup_Simulation，直接改参数
MWS.In.PLA = new_pla_profile;
assignin('base','MWS',MWS);
sim(MDL);   % 只花 8.06s，省 3.53s
```

**预期**：8.06 s/步（省 30%）。

### 4.3 方案 C：只评估不搜索（最务实）

**接受 Simulink 慢，但只用在闭环评估，不在 MPC 内部预测。**

| 用途 | 工具 | 耗时 |
|---|---|---|
| **MPC 内部预测**（每步 32 候选）| 神经代理模型（GRU/PC-RSSM）| **<1 ms** |
| **闭环评估**（每控制周期 1 次）| Simulink 真 step | 8 s |

**闭环评估成本**：
- 60 s 评估 = 571 步 × 8 s = **76 分钟**
- 10 个场景 = **12.7 小时**

**这是可接受的**（相当于训练一个模型的成本）。

### 4.4 方案 D：降采样控制周期

**若用 1.05 s 控制周期**（10× 慢）：
- 仿真 0.105s 和 1.05s 耗时相同（都是 8 s，因瓶颈是固定开销）
- **不解决问题**

**结论：降采样无效**（因为耗时与仿真时长无关）。

### 4.5 方案对比总表

| 方案 | 单步耗时 | 能否实时 | 工作量 | 风险 |
|---|---|---|---|---|
| **A. Simulink Coder** | **1–10 ms** | ✅ | 中（需验证兼容性）| 自定义块可能不支持 |
| B. 省 Setup | 8.06 s | ❌ | 小 | 无 |
| **C. 只评估** | 8 s（仅评估）| N/A | **小（现成）** | 无 |
| D. 降采样 | 8 s | ❌ | 无 | 无效 |

**推荐顺序：C（立即可用）→ A（性能优化）**

## 五、S 路线控制规范（任务 2）

### 5.1 动作定义

```yaml
control_level: S                      # 上层监督控制（保留 EEC）
action:
  name: PLA
  type: absolute                      # ★ 绝对指令，不是增量
  physical_meaning: 油门杆角度
  unit: deg
  injected_at: MWS.In.PLA
  bound_min: 40.0                     # 基于数据覆盖（组 A/C 最小 40）
  bound_max: 80.0                     # 基于数据覆盖（组 A/C 最大 80）
  nominal: 55.0                       # 标称工作点
  slew_rate_limit: 2.0 deg/s          # 待验证（见 §5.3）
  held_during_step: true              # 控制周期内保持恒定
```

**为什么是绝对值而非增量**：
- `MWS.In.PLA` 是时间序列，天然是绝对值
- 增量需要内部累积，增加状态复杂度
- 绝对值更易验证（可直接读回 `out_Dyn.in.PLA`）

### 5.2 控制周期

```yaml
sampling_interval_s: 0.105            # 与现有数据集一致（step=7 × 0.015）
```

**依据**：
- 与 26 条训练数据的采样率一致（`dt=0.105`）
- Wfdmd 63% 响应时间 0.575 s → 0.105 s 采样足够密

### 5.3 变化率限制（待验证）

**当前无限制**。从数据看：
- 组 A 的 step 轨迹：**30 deg/步**（阶跃式）
- 组 A 的 msin/ramp：**0.03–0.10 deg/步**（连续）

**建议**：
```yaml
slew_rate_limit: 2.0 deg/step          # = 19 deg/s，保守
```

**依据**：
- 阶跃测试用的 ±2 deg 是安全的（未见饱和）
- 实际 MPC 应更保守

**⚠️ 需验证**：是否有隐藏的速率限制器（EEC 内部）。
